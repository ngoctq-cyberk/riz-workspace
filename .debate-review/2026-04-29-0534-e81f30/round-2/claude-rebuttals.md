# Round 2 — Claude rebuts Codex

### R-F-001: Challenge videos are excluded from `hasVideo` and feed media

- **Stance**: agree
- **Reasoning**: This finding is correct and is the most important issue in the diff — I missed it in round 1. Verified at `riz-be/apps/nest/libs/challenge/src/challenge.service.ts:484-496`: `createProjectVideosFromVimeo` persists challenge videos with `type: MediaType.VIDEO, usage: MediaUsage.PROJECT_ATTACHMENT`. Meanwhile every new `_count` selector added in this diff (admin-trending.service.ts lines 283-287, 520-524, 560-564, 662-666, 893-897) filters on `usage: MediaUsage.PROJECT_IMAGE`. So for any challenge submission whose only video came through the Vimeo pipeline, `_count.attachments === 0` and `hasVideo` collapses to `false`. The damage is broader than the `hasVideo` flag: the `attachments` selection in the same include block also uses `where: { usage: MediaUsage.PROJECT_IMAGE, ...}` (admin-trending.service.ts:281-284 and the four parallel sites), so the video is dropped from `images[]` entirely — it never reaches the FE `MediaCarousel` regardless of any FE fix. This matches the design doc intent ("video challenge submissions must play in art-feed") and breaks it. The two stores have diverged: image-style media goes through `PROJECT_IMAGE`, Vimeo videos go through `PROJECT_ATTACHMENT`, and the new query contract assumes everything is `PROJECT_IMAGE`. Either the writer (challenge.service.ts) or the readers (admin-trending + project.service) must be reconciled before this feature ships.
- **Counter-evidence**: agree — no counter. Confirming evidence: `riz-be/apps/nest/libs/challenge/src/challenge.service.ts:491` (`usage: MediaUsage.PROJECT_ATTACHMENT`) vs diff line 442 in admin-trending.service.ts (`usage: MediaUsage.PROJECT_IMAGE`). Also note the existing `attachments: { where: { usage: MediaUsage.PROJECT_IMAGE }, ... }` selectors at admin-trending.service.ts:277-282 (and the four duplicates) already excluded videos pre-diff; the diff did not fix that side either.

### R-F-003: Active video state is not cleared when carousel page changes

- **Stance**: agree
- **Reasoning**: This is essentially the same defect as my F-005, expressed slightly differently. Codex frames it as "previous video keeps playing offscreen / state stays true past the swipe"; I framed it as "second video auto-plays without an explicit tap". Both describe the same underlying flaw: `isVideoActive` is a single boolean, set once on tap, only reset on `project.id` change (project-feed-item.tsx:61-63). Verified at `riz-app-v2/components/media-carousel/media-carousel.tsx:57`: `isActive = isVideoActive && index === activeIndex.value`. So the previously active video does pause the moment `activeIndex` changes (good), but the new visible video immediately becomes active because `isVideoActive` is still true (bad). Codex's "keeps playing offscreen" wording is slightly imprecise — `index === activeIndex.value` does gate playback to the visible page — but the broader correctness concern (state outlives user intent) is valid. Severity medium feels appropriate; I had it as low only because the FE fix is tractable, but the user-visible behaviour is genuinely confusing.
- **Counter-evidence**: agree — partial overlap with my F-005; orchestrator should merge. Note the small imprecision in Codex's claim (videos do pause when scrolled offscreen due to the `index === activeIndex.value` check), but the residual issue (next video auto-plays without tap) stands.
