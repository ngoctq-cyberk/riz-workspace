### P-F-006: Video URL fallback discards `mediumUrl` when present and falls through to raw `url`

- **Position**: partial
- **Reasoning**: Codex correctly points out that the title and the phrase "discards mediumUrl when present and falls through to raw url" mischaracterise the `??` operator — the operator does prefer `img.mediumUrl` and only falls back to `img.url` when the former is nullish. That part of my original wording was wrong and I concede it. However, the substantive concern remains and is in fact reinforced by Codex's own counter-evidence (`media-carousel-item.tsx:71` passes only `item.url` to `CommunityFeedInlineVideo`): the mapping at `project-feed-item.tsx:69-71` collapses both URLs into a single `url` field while explicitly setting `mediumUrl: undefined` for videos. Once the HLS URL has been written into `MediaItem.url`, the original MP4 (`img.url` from the BE) is no longer reachable anywhere in the FE state — there is no `hlsUrl` field, no second slot. The player therefore has exactly one URI to attempt, and if HLS playback fails there is nothing to fall back to. The bug isn't the `??` — it is the lossy projection from `{ url, mediumUrl }` (BE) to a single `url` (FE) for videos. Narrowing the claim accordingly.
- **Updated claim**: For `VIDEO` items the mapping at `project-feed-item.tsx:69-71` writes the HLS URL into `MediaItem.url` and explicitly nulls `mediumUrl`, collapsing BE's two-URL contract (`url` = MP4, `mediumUrl` = HLS) into a single value. Because `MediaCarouselItem` (`media-carousel-item.tsx:71`) only passes `item.url` to the inline video player, the original MP4 source is lost from FE state — if HLS playback fails there is no fallback URL available. Suggest preserving both URLs explicitly on `MediaItem` (e.g. keep `url = img.url` and `mediumUrl = img.mediumUrl` for videos, then have the player prefer `mediumUrl` with `url` as fallback).

### P-F-009: BE `ProjectImageEntity.type` is nullable but FE type is `"IMAGE" | "VIDEO"` (no null) — mismatched optionality

- **Position**: partial
- **Reasoning**: I verified `schema.prisma:568` and Codex is right — `Media.type` is declared `MediaType` without `?`, so Prisma will never produce a `null` for `media.type`. The runtime portion of my original claim ("BE will emit `null`") is therefore incorrect for any record that came through Prisma; I concede that. What remains valid is the contract-shape mismatch at the API surface: `project.entity.ts:98-100` annotates the field as `MediaType | null` (with `ApiPropertyOptional`), so the published OpenAPI contract advertises `null` as an allowed value, while the FE type at `riz-app-v2/lib/api/projects/types.ts:102` only models `"IMAGE" | "VIDEO" | undefined`. Any future code generation off the OpenAPI schema, or any non-Prisma path that constructs `ProjectImageEntity`, can legally emit `null` per the declared contract — and the FE has no null branch. The fix is one-sided now: tighten the BE entity to `type: MediaType` (non-null) so the documented contract matches the actual schema; no FE widening is needed. Demoting from "schema may produce null" to "entity declaration is overly permissive vs schema".
- **Updated claim**: `ProjectImageEntity.type` is declared `MediaType | null` at `project.entity.ts:98-100`, but the underlying `Media.type` column at `prisma/schema.prisma:568` is non-nullable. The entity declaration is therefore broader than the schema and broader than the FE type (`types.ts:102`, no `null` branch). Tighten the entity to `type: MediaType` (non-nullable, with `@ApiProperty` instead of `@ApiPropertyOptional`) so the published OpenAPI contract matches both the DB schema and the FE expectation. This is purely a contract-tightening cleanup; runtime is unaffected as long as data flows through Prisma.
